## 3. Адресные события глав и общий прогресс без полного обхода (P0, развитие Play/Pause)

**Запрос пользователя:** не заставлять одну кнопку Play/Pause ждать обновления сотен глав. При скачивании одной главы менять только её карточку и общий прогресс произведения; сохранять общий прогресс локально, не создавая лишних потоков и частой записи JSON. **Статус:** утверждаемая архитектура для реализации в v1.11.176, исходники v1.11.175 пока не изменяются.

### 3.1. Почему текущая система делает лишнюю работу

По исходному архиву `PROChitalka-v1.11.175-beta-CLEAN-GradleCompileHotfix-Full-Source.zip`:

- `DownloadChangeBus.publish(id)` уведомляет только об изменении **всего произведения**. `UnifiedDownloadManagerActivity.downloadListener` через 350 мс вызывает `reload()` целиком, который делает `DownloadsRepository.loadOne`, `readRows` (пересборка всех глав), `buildInfo`, запись двух снимков на диск и `adapter.submit(rows)`. При частых событиях это лишние O(N) операции.
- В `UnifiedDownloadManagerActivity.control()` после команды есть дополнительный `postDelayed(this::reload,450)`; запуск управления сцеплен с тяжёлым обновлением экрана.
- `DownloadWorker` уже посылает прогресс примерно раз в 600 мс, но `BookImportManager.put` периодически пересохраняет **все** задачи. `MangaLibStorage.liveProgress` уже использует полезный in-memory overlay, однако внешний bus всё равно содержит только ID книги.
- Менеджер аудиокниг при обновлении одной позиции перебирает список состояний, а менеджер Edge TTS для строк может снова получать `ChapterSnapshot` через SAF. Не запускать этот путь на каждом байте/странице.

### 3.2. Три независимых уровня: команда, прогресс, долговременное состояние

1. **DownloadCommandController** — Play/Pause/Cancel/Enqueue, немедленно отвечает UI состоянием `STARTING/QUEUED/PAUSING`; фактический запуск в существующих фоновых исполнителях. Команды сериализуются по `downloadId` с `commandGeneration`; не ожидать ни списка глав, ни SAF.
2. **DownloadProgressTracker** — лёгкая *проекция в памяти* для каждого `downloadId`: map `chapterId -> ChapterProgress`, агрегатные счётчики и последняя ревизия. Обновляется только событием от конкретного worker, без чтения файлов или рефетча списка. Это не дополнительный источник истины о завершении глав.
3. **DownloadProgressStore** — маленький долговременный снимок **общего** прогресса по книге (и метаданные активной главы) в приватном `AtomicFile` JSON. Долговечные статусы глав остаются в действующих хранилищах загрузчиков и, для Edge TTS, в зафиксированном SAF-индексе. Не создавать полную вторую JSON-копию списка глав при каждом изменении процентов.

Разделить события: `COMMAND_STATE`, `CHAPTER_PROGRESS`, `CHAPTER_COMMITTED`, `BOOK_PLAN_CHANGED`, `ERROR`, `RESET`. Расширить `DownloadChangeBus` новым типизированным каналом, **сохранив совместимость** прежнего `publish(id)` для редких структурных событий и старых слушателей. Все события должны содержать `downloadId`, `chapterId` (если применимо), `generation/sequence` и краткую текущую информацию, а не массив всех глав. Один общий coalescing scheduler, не Handler/Thread на каждую главу.

### 3.3. O(1) изменение общего прогресса

При открытии/изменении состава очереди **один раз** вычислять `denominator = sum(weight_i)` и `numerator = sum(weight_i * fraction_i)`, где `fraction_i` от 0 до 1, а `weight_i` — фиксированный вес главы в данной очереди; по умолчанию `1`. Допускаются известные стабильные веса (например, объём текста/число слов Edge TTS), если они известны **до начала** расчёта. В обычном интерфейсе можно показывать отдельно «Готово глав X из N» и «Общий прогресс Y%». Не смешивать метрики отдельных источников без определения общего плана.

При событии главы `i` с новым `fraction_i'` менять **только вклад этой главы**:

`numerator' = numerator + weight_i * (fraction_i' - fraction_i)`;
`overallPercent = clamp(100 * numerator' / denominator, 0, 100)`.

Если вес или состав очереди меняется, обновить агрегат **однократно по событию `BOOK_PLAN_CHANGED`**. Прогресс хранить внутренне в целых тысячных/базисных пунктах, чтобы избежать ошибок округления; пересчёт полного списка не делать в каждом progress callback. Нужны `completedChapters`, `downloadedBytes`, `activeChapter` и `running/queued/paused` отдельно.

Для каждого типа сохранять точный смысл единиц: `AUDIO`/`LINK` — байты, если известен стабильный total, иначе прогресс отдельного файла; `MANGA` — подтверждённые страницы в главе / известное число страниц; `RANOBE/RANOBES` — этапы записи и подтверждённые завершённые главы; `EDGE` — покрытие сегментами/словами и окончательное подтверждение SAF-индекса. При неизвестном `total` показывать неопределённый прогресс и количество готовых глав, **не выдумывать проценты**. 100% отдельной главы и книги — только после устойчивого commit результата (MP3/CBZ/HTML/index), не по достижению 100% сетевого приёма.

**Идемпотентность:** обработчик хранит `lastSequence` и старый вклад `chapterId`; повторный или запоздавший callback не добавляет прогресс второй раз. `generation` для нового запуска/сброса, `sequence` для упорядочения. Перезапуск загрузки может уменьшить процент только по осмысленному событию сброса, не вследствие устаревшего снимка.

### 3.4. Обновление только двух визуальных элементов

В открытом менеджере **один** `CHAPTER_PROGRESS` обновляет:

- Только строку активной главы через `RecyclerView.Adapter.notifyItemChanged(position, PAYLOAD_PROGRESS)` либо эквивалент, без замены списка, пересоздания кнопок или чтения `DocumentFile`. Использовать стабильный ID главы и индекс `chapterId -> adapterPosition` (перестраивается только при изменении состава/сортировки).
- Только верхний `ProgressBar`, проценты, счётчик готовых глав и при необходимости скорость/статус. Не трогать название, обложку, `Info` и значения других глав.

Отдельный `CHAPTER_COMMITTED` дополнительно обновляет галочку/статус именно этой главы, `completedChapters` и общий прогресс. `BOOK_PLAN_CHANGED` допускает разовую фоновую пересборку списка и `DiffUtil`, но не по таймеру. `Info` и проверку SAF выполнять только при открытии вкладки/смене папки/ошибке, а не на каждый chunk.

**Частота событий:** скачивающий worker может часто получать байты/страницы, но UI-события объединяются по `downloadId + chapterId`. Для видимого экрана целевой максимум около **4–5 обновлений/с** на активную главу (одно каждые 200–250 мс, немедленно — смена состояния/завершение/ошибка/нажатие). Если экран не видим, обычные UI-события не гонять; при `onResume` получить последнее состояние из in-memory cache и при необходимости один раз сверить ревизию. Foreground notification обновлять отдельно, с меньшей частотой (например, раз в 1–2 с), кроме финального события. Не создавать по таймеру фоновый полный аудит папок. Эти интервалы — начальные ориентиры, корректируются по профилированию.

### 3.5. Локальный JSON прогресса — малый и безопасный

**Кэш — не второй архив файлов.** Например `filesDir/download_progress_v176/<bookKey>.json`, сохранять компактный снимок вида:

```json
{
  "schema": 1,
  "downloadId": "audio:example",
  "revision": 42,
  "plannedChapters": 120,
  "completedChapters": 37,
  "weightedDone": 3750,
  "weightedTotal": 12000,
  "downloadedBytes": 91827364,
  "activeChapterId": "chapter-38",
  "activeProgress": 48,
  "state": "RUNNING",
  "updatedAt": 1794920000000
}
```

`weightedDone/weightedTotal` в примере условны (масштаб фиксированных единиц), не должны восприниматься как независимый реестр завершения глав. При необходимости `activeChapterId` может быть null. Не включать в этот JSON полные MP3/WordBoundary, оглавление, тысячи файлов или `JSONArray` всех задач.

- Хранить текущее состояние в памяти; JSON записывать **пакетно** в одном ограниченном IO executor по dirty-флагу с дебаунсом примерно 3–5 с **только во время изменений**; никогда не писать из UI и не делать `SharedPreferences.commit()` на каждом chunk.
- Немедленно сбрасывать контрольную точку на фоне при `CHAPTER_COMMITTED`, `PAUSE`, `CANCEL`, `FAILED` и завершении книги. До появления 100% обязательным остаётся успешный commit реального файла/индекса; кэш-снимок не должен подменять его.
- Использовать Android `AtomicFile` или эквивалент атомарной замены, версионировать схему и использовать ключ, отличающий книгу и источник (включая очереди по разным папкам). Для SAF-файлов хранить ссылки/индексы в существующих источниках, не в UI-кэше.
- При запуске мгновенно показать последний снимок как **предварительный**, затем **один раз** сверить его с авторитетным хранилищем, если ревизия/путь/схема изменились, был аварийный выход или не удалось подтвердить завершение. Не запускать хеширование сотен MP3 при каждом открытии; проверять спорные или незавершённые записи адресно.
- После аварийного завершения допускается потеря нескольких секунд промежуточного визуального процента, но не готовых файлов, не флагов «готово», не команды Pause и не сохранённой очереди.

### 3.6. Источники изменений: одна запись и одно событие

Workers `DownloadWorker`, `EdgeFullBookService`, `MangaLibDownloadWorker`, `RanobeLibDownloadWorker`, `RanobesDownloadWorker`, `DirectLinkDownloadService` отправляют `CHAPTER_PROGRESS(bookId,chapterId,done,total,bytes,state,sequence)` в общий трекер без ожидания диска. При записи очереди не пересериализовать весь список глав на каждой странице, не выполнять лишний SAF-обход. У MangaLib сохранить существующий live-overlay, подключить его к адресным событиям вместо повторного чтения всех глав. Существующий `DownloadChangeBus.publish(bookId)` продолжает обслуживать изменения структуры и совместимость.

Если сервис живёт в отдельном процессе, локальный in-memory bus не подходит как единственный транспорт: добавить межпроцессную доставку или чтение сохранённой версии при возвращении экрана. Не запускать фоновую службу только ради отображения процентов.

### 3.7. Очередь без лишних потоков, защита управления

- Для управления Play/Pause — **одна ограниченная последовательная очередь команд**, не связанная с выполнением тяжелого `reload`; сетевые workers продолжают использовать существующий WorkManager/Foreground Service. Не создавать executor на каждую главу.
- Для записи компактного JSON — один сериализованный исполнитель/очередь с коалесцированием по книге, максимум один ожидающий flush на книгу. При быстрых событиях обновлять последнюю запись, а не добавлять в очередь 200 операций.
- `PLAY` меняет UI сразу на `STARTING`, затем подтверждение — `QUEUED/RUNNING`; `PAUSE` меняет сразу на `PAUSING`, затем подтверждение — `PAUSED`. Старые события не перетирают новое намерение по `commandGeneration`. При отсутствии сети статус «В очереди / Ожидание сети»; Pause доступна.
- Не читать SAF и не пересоздавать хранилища при каждом изменении прогресса. При `onPause/onDestroy` отписывать UI-подписчика, но загрузка и фиксирование progress/checkpoint продолжаются.

### 3.8. Приёмка и измерения

1. Книга с **500 главами**: при скачивании одной обновляются ровно одна видимая строка и общий прогресс; повторных `readRows()` и `adapter.submit()` на каждый chunk нет. После выхода и возврата данные совпадают с устойчивым источником.
2. Книга с 1000 фрагментов Edge TTS: прогресс учитывает только готовые сегменты; только после commit главы появляется галочка, 100% не возникает на 99% стадии публикации.
3. 1000 callbacks прогресса подряд: не создаются 1000 IO-записей/перерисовок. Проверить верхние границы частоты UI и checkpoint.
4. Play/Pause/Play, смена вкладки, уход приложения в фон, повторное открытие, убийство процесса, отключение сети, плохой SAF, смена папки, две книги в очереди: нет дублей, устаревших процентов, пауз не того задания и ложных 100%.
5. Во время активной загрузки быстрый скроллинг списка остаётся плавным; сборки debug/release измеряются в Perfetto/StrictMode, а `:app:assembleRelease` обязательно запускается в GitHub Actions.
6. Сравнить с v1.11.175 счётчики `reload`, `readRows`, SAF-вызовов, JSON-коммитов, перерисовок строк и время до реакции Play. Метрики только debug, без постоянного логирования каждого байта в release.

**Приоритет:** P0 — адресные события/агрегат/UI и немедленная реакция Play; P1 — атомарный summary cache, пакетная запись, восстановление и оптимизация всех источников. Новая схема не отменяет сохранность и существующие гарантии записи.
