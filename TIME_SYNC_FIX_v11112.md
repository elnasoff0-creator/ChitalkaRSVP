# ПРОЧиталка v1.11.112-beta CLEAN — исправление Edge TTS MS time sync

**Редакция:** 28 октября 2026 г.
**Основа:** исходный проект v1.11.112-beta CLEAN с пунктом «Показать лог-файл».
**Версия не менялась:** `versionName = 1.11.112-beta`, `versionCode = 11212`.

## 1. Почему исправление необходимо

В Quickify на скриншотах ошибка `429 Too Many Requests` видна в операции `MS_TIME_SYNC`, а не в обязательном потоке синтеза MP3. Отдельный сервис проверки времени может не работать, пока текущий MP3-кэш и воспроизведение остаются исправны. **Это не означает, что 429 на WebSocket-синтезе Microsoft Edge TTS можно игнорировать.**

Ранее ПРОЧиталка рассчитывала `Sec-MS-GEC` по системным часам Android и могла скорректировать смещение по заголовку HTTP `Date` только при ошибке `403`. Смещение оставалось исключительно в оперативной памяти и терялось при перезапуске.

## 2. Новое поведение

1. При запуске приложения `ReaderApp` инициализирует `EdgeServerClock` через `EdgeClockPreferences`. Если есть корректное смещение с возрастом менее 24 часов, оно немедленно используется для расчёта следующего GEC-токена.
2. Каждый **реальный** WebSocket-handshake к Microsoft собирает время его начала и конца. Если сервер возвращает заголовок `Date` при `101 Switching Protocols`, он передаётся в `EdgeServerClock.observeHttpDate(...)`.
3. Разбор даты, проверка образца и обновление смещения выполняются **в отдельном служебном потоке**, не ожидаются проигрывателем. Никаких дополнительных запросов к URL `MS_TIME_SYNC` не создаётся.
4. При ошибке `403` сохраняется существующая коррекция времени и одна немедленная повторная попытка, только если новый токен отличается от отвергнутого.
5. При наличии HTTP `Date` в ошибке `429` образец можно пассивно использовать, но **не** создавать повторный запрос ради часов. Обычное поведение 429 синтеза не изменено (без автоматической повторной отправки, локальный лимит ожидания до 500 мс).
6. Коррекция применяется только к формированию `Sec-MS-GEC`. Системное время Android, текущий Media3-плеер, WordBoundary и пользовательский текст не изменяются.
7. Сдвиг сохраняется локально, без токенов, SSML и содержимого книги, через `SharedPreferences.apply()`.

## 3. Защита от неверного времени

- Строго разбирается стандартная HTTP-дата в GMT; недействительный или отсутствующий `Date` игнорируется.
- Образцы после длительного handshake более 15 секунд игнорируются как ненадёжные.
- Слишком большие отклонения (более 48 часов) отбрасываются, чтобы не портить токены.
- Запоздавшее асинхронное событие не может перезаписать более свежий образец.
- Сохранённая поправка старше 24 часов не восстанавливается.
- Если заголовка `Date` нет, озвучивание продолжает работу со стандартными часами Android; дополнительное подключение ради синхронизации **не** выполняется.

## 5. Что **не изменено**

- `EdgeSpeechQueue` и лимит **500 мс** локального ожидания; новая адаптивная обработка 429 не добавлена.
- Размер пула Edge WebSocket: до **4** ресурсов; фоновых генераций: до **2**.
- Переиспользование WebSocket между последовательными `turn.end` и сохранение MP3-кэша.
- Потоковое MP3 через Media3, WordBoundary, WPM/скорость, озвучка и выбор текста.
- Экран **«Настройки → Аудио → Диагностика → Показать лог-файл»**.
- Ни один новый таймер не блокирует старт Play. Ограничения самого сервера Microsoft сохраняются.

## 6. Лог-файл

Новые строки могут выглядеть так:

```text
2026-10-28 22:30:00.123 | CLOCK | saved offset loaded skew_ms=599200
2026-10-28 22:30:05.021 | WS | open id=1
2026-10-28 22:30:05.022 | CLOCK | server date synchronized via=ws101 offset_ms=599610
2026-10-28 22:30:05.130 | EDGE | first_mp3_frame elapsed_ms=...
```

Надпись `ws101` означает, что `Date` получен вместе с успешным WebSocket-handshake. `ws429` — лишь возможный пассивный образец времени из ответа об ограничении, но **не** успешный TTS-синтез.

Запись не включает исходный текст книги, заголовки авторизации и сетевой URL с ключами. `CLOCK` не создаёт HTTP-запросов.

## 7. Тестирование

Выполнены **25 из 25** QA shell-скриптов, включая новый `qa/test_edge_clock_sync.sh`. Тесты охватывают:

- HTTP 101, пассивное чтение Date из 429, отсутствие блокирующего ожидания;
- сохранение смещения, повторную загрузку после перезапуска, отбрасывание устаревших образцов;
- сценарии HTTP 403, фиксированный 500-мс предел, отсутствие автоматического retry для 429;
- WebSocket Pool и повторное использование, предварительную генерацию, WordBoundary, Media3-буфер, журнал диагностики;
- синтаксис Java; адаптер `SharedPreferences` проверен отдельно с JVM-заглушками Android.

**Важно:** без установленного Android SDK полноценный `assembleDebug/Release`, запуск на телефоне и сетевой обмен с реальным сервером Microsoft **не выполнялись**. JVM-тесты не доказывают фактическое снижение задержки Edge TTS на вашем устройстве.

## 8. Инструкция по проверке на телефоне

1. Собрать и установить исходный проект с Android SDK и своей подписью.
2. Открыть книгу, запустить Edge TTS, прослушать первое предложение и переключиться на другое.
3. Открыть **Настройки → Аудио → Диагностика → Показать лог-файл**.
4. Найти `CLOCK | server date synchronized via=ws101`; если его нет, сервер мог не прислать `Date` — это не блокирует синтез.
5. Перезапустить приложение и проверить `CLOCK | saved offset loaded ...`.
6. Проверить сохранение подсветки WordBoundary и отсутствие новых задержек при переходе между предложениями.
7. Если появляется `HTTP 429 from synthesis WebSocket handshake`, это реальное ограничение синтеза, а не отдельный `MS_TIME_SYNC`.
