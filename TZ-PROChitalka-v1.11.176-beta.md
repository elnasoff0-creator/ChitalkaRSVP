## 1. Обязательное изменение — Dynamic Version в GitHub Actions (P0)

### 1.1. Цель и обнаруженная причина

Устранить рассинхронизацию между действительной версией APK, названием скачиваемого файла, именем GitHub Release, тегом и контрольной суммой. В проекте v1.11.175 `app/build.gradle` содержит `versionCode 17500` и `versionName '1.11.175-beta'`, но прежний workflow публиковал APK под захардкоженным именем `ChitalkaRSVP-v1.11.58-beta.apk`. Одно лишь имя файла в GitHub Assets не доказывает старую версию **внутри** APK; её устанавливать по манифесту.

### 1.2. Единый источник версии

1. Версия приложения задаётся в `app/build.gradle` / `defaultConfig` (`versionCode` и `versionName`), без второго ручного номера в YAML, скриптах подписи, названии APK и SHA-файле.
2. После `:app:assembleRelease` фактические `versionName` и `versionCode` извлекать **из реально собранного APK** с помощью `aapt dump badging` (или эквивалента `apkanalyzer`). Не формировать файл только по тегу, `GITHUB_REF_NAME` либо тексту release notes.
3. Название конечного файла формировать как `ChitalkaRSVP-v${versionName}.apk`. Пример будущей версии: `ChitalkaRSVP-v1.11.176-beta.apk`.
4. На экранах приложения, где отображается версия, получать её из `PackageManager` / `BuildConfig`, а не из отдельной константы, копии заголовка или имени APK. Проверить фактические места отображения при реализации — не предполагать их наличие.
5. Значение `versionCode` должно оставаться монотонно возрастающим для новых устанавливаемых релизов; проверять, что новый код выше последней опубликованной версии.

### 1.3. Проверка соответствия Git-тега и APK

1. При запуске по тегу `v...` строго сравнивать `${GITHUB_REF_NAME#v}` с `versionName`, прочитанным из APK; если значения отличаются — **заваливать job ДО публикации** с понятным сообщением. Например, тег `v1.11.175-beta` с APK `1.11.176-beta` — ошибка.
2. При обычном push в `main` либо `workflow_dispatch` создавать подписанный артефакт, но не создавать GitHub Release без корректного релизного тега.
3. Убедиться, что сборка выполняется из коммита выбранного тега, а не из случайной более поздней ветки. Релиз не должен использовать APK из другого commit/ref.
4. Имя GitHub Release, номер в релизном описании, тег и APK должны описывать одну и ту же версию. Метка GitHub `Latest` сама по себе не подтверждает внутреннюю версию APK.

### 1.4. Подпись, контрольные суммы и артефакты

1. Сохранить уже работающие шаги Gradle 8.7 / JDK 17 / Android SDK, подписание через `zipalign` и `apksigner`, получение секретов из GitHub Secrets, без публикации ключей и паролей в логах.
2. После подписи выполнять `apksigner verify`; дополнительно читать `versionName/versionCode` из **подписанного APK** и сравнивать с данными до подписи. При расхождении — останавливать публикацию.
3. Генерировать `SHA256SUMS.txt` именно для финального подписанного APK и использовать в нём то же динамическое имя, что в Release Assets.
4. Передавать путь к APK между job steps через `GITHUB_ENV` или `GITHUB_OUTPUT` (одно вычисление и одно имя), не дублировать строку имени в `upload-artifact`, `gh release upload/create`, проверке подписи и расчёте SHA.
5. Публикация должна прекращаться, если APK отсутствует, нулевого размера, подпись не проходит проверку, версия не извлечена или не совпадает с тегом.
6. При повторной публикации **того же тега** заменять новую версию ассетов безопасно: только после успешной проверки и загрузки APK убрать старые несовпадающие `.apk` именно этого GitHub Release; не удалять другие релизы и необязательные материалы без отдельной необходимости. Не оставлять рядом `v1.11.58` и `v1.11.176` под одним и тем же тегом.
7. Релизы с суффиксами `-beta`, `-alpha`, `-rc` отмечать как prerelease; обычный релиз без этих суффиксов публиковать как stable. Не менять версию приложения из-за типа GitHub Release.

### 1.5. Работа с репозиторием и исходным архивом

1. Изменить действующий `.github/workflows/release.yml` репозитория. Файл `release-dynamic-version.yml`, подготовленный для предыдущего обсуждения, использовать как **референс**, а не выдавать за уже внедрённый workflow.
2. В референсе реализовано динамическое имя по `aapt`, но **не реализовано жёсткое сравнение версии APK с релизным тегом**. При следующей реализации добавить это условие и проверку подписанного манифеста.
3. Проверить, что `.github/workflows/release.yml` реально включён в поставляемый исходный проект следующей версии, либо документировать его отдельной частью релизного комплекта, если у пользователя workflow поддерживается непосредственно в GitHub. Ранее архив полного исходного проекта v1.11.175 не содержал `.github/workflows`.
4. Не переписывать существующие пользовательские GitHub Secrets, права репозитория и другие независимые workflows. Для существующего workflow применять адресные изменения.
5. Не править Gradle-манифест только ради переименования файла: `versionCode/versionName` обновляются один раз для нового релиза, а название APK выводится из собранного результата.

### 1.6. Обязательные проверки и критерии приёмки

| Сценарий | Ожидаемый результат |
|---|---|
| Сборка v1.11.176-beta | `aapt`/`apkanalyzer` показывает `versionName=1.11.176-beta`, `versionCode=17600` |
| Имя финального APK | `ChitalkaRSVP-v1.11.176-beta.apk`, без старого `1.11.58` |
| Тег `v1.11.176-beta` и такой же APK | Подпись, SHA, артефакт и GitHub Release проходят |
| Тег `v1.11.175-beta`, APK `1.11.176-beta` | Публикация отклонена с ясной ошибкой |
| Push в `main` без тега | Есть проверяемый артефакт; новый GitHub Release не создаётся |
| Повторная публикация одного тега | В Release остаётся один корректный APK этой версии, SHA соответствует ему |
| Повреждённый / отсутствующий APK или ошибка подписи | Выполнение завершается ошибкой, релиз не публикуется |
| Отображение версии внутри установленного приложения | Соответствует версии в манифесте APK |
| Переход с v1.11.175 на v1.11.176 | Установка обновления возможна, пользовательские данные и выбранные SAF-папки сохраняются |

Перед передачей полноценного релиза выполнить `gradle --no-daemon :app:assembleRelease --stacktrace --console=plain` в CI с Android SDK, проверить `aapt dump badging` для подписанного APK, `apksigner verify`, `sha256sum -c SHA256SUMS.txt` и ссылку GitHub Release. **Локальная проверка YAML и Java-синтаксиса не заменяет сборку Android.**

### 1.7. Правило для всех будущих версий

Любое изменение `versionName` должно автоматически отражаться в файле APK, SHA256SUMS, артефактах CI и GitHub Release без ручного изменения нескольких констант. Не допускать в workflows шаблонов с зафиксированными номерами наподобие `v1.11.58-beta.apk`.

## 2. Менеджер загрузок — мгновенная реакция Play/Pause, запуск без блокировки UI (P0)

**Статический аудит:** исходный `PROChitalka-v1.11.175-beta-CLEAN-GradleCompileHotfix-Full-Source.zip` (Android Java). Жалоба пользователя: после нажатия Play кнопка долго не переключается на Pause и создаёт впечатление, что запуск не сработал. Длительность задержки на устройстве не измерялась. Устранить задержку в **общем менеджере** и обеспечить одинаковые, отзывчивые состояния в связанных экранах.

### 2.1. Обнаруженный путь задержки и кодовые риски

1. `UnifiedDownloadManagerActivity.control()` (`~495–513`) выполняет действия сразу из `OnClickListener`, в том числе синхронные `MangaLibQueue.resume`, `RanobeLibQueue.resume`, `RanobesQueue.resume`. Там же без немедленного обновления кнопки запланирован `main.postDelayed(this::reload,450)`. Кнопка меняется лишь в `refreshHeader()` (`~350–365`) при получении `selected.running` из завершённого `reload()`.
2. `reload()` (`~209–237`) обращается в отдельном дисковом executor к `DownloadsRepository.loadOne`, `readRows`, `buildInfo`, сохраняет `DownloadRowsSnapshot` и `DownloadInfoSnapshot`, и только затем обновляет заголовок. Непосредственно после Play не нужно ждать загрузки десятков/сотен строк и SAF для обновления одной иконки. Возможна также задержка из-за занятого очередью `disk` executor; наличие `queuedReload` дополнительно сериализует обращения.
3. `MangaLibQueue.resume()` (`~62–69`) получает все задания, затем `enqueue()` (`~17–38`) вызывает `MangaLibStorage.put` **для каждой** выбранной главы, что пересобирает JSON всех заданий и делает синхронный `SharedPreferences.commit()`, плюс формирует цепочку `WorkManager`. При длинной манге это тяжёлая синхронная работа на UI-потоке.
4. `RanobeLibQueue.resume/enqueue` и `RanobesQueue.resume/enqueue` читают все или относящиеся к произведению задания, формируют списки и WorkManager-цепочки, записывают общее состояние (`putAll`); они также вызываются прямо из UI-кнопки общего менеджера.
5. `DownloadWorker.onStartCommand()` (`~19–21`) выполняет `lookup` и `BookImportManager.put` с полным JSON/`commit` **до** запуска загрузочного потока. `EdgeFullBookService.onStartCommand()` (`~100–132`) читает весь список заданий и сохраняет очередь в обработчике команды; это нельзя делать дорогим путём основного UI-потока процесса.
6. `DownloadsRepository.fromEdge` учитывает `running` только при `EdgeFullBookService.isServiceAlive()` И подходящем статусе; только что принятая, но ещё не запущенная очередь может всё ещё изображаться как Play. При других источниках также различаются `queued`, `running` и `paused`; управление не должно зависеть исключительно от фактического активного HTTP-потока.
7. **Отдельный функциональный риск аудиокниг:** `DownloadWorker` использует одну общую переменную `thread`, `source`, `halt`; `START` при живом `thread` просто возвращает `START_STICKY`, не ставя новое произведение в очередь. `PAUSE` безусловно устанавливает общий `halt=true` до проверки принадлежности активному `source`. При нескольких произведениях возможны игнорирование Play и остановка не того задания. Исправлять в рамках того же пункта без параллельной скачки всех книг.

### 2.2. Правильная архитектура — реакция UI отдельно от фоновой работы

1. При нажатии Play **немедленно** на UI изменить состояние кнопки с «Play» на **«Запуск…» / значок Pause в состоянии `STARTING`** (с доступным повторным нажатием для отмены/паузы), без ожидания `loadOne`, сканирования SAF, подготовки обложек и WorkManager. Не обозначать сетевую загрузку уже начатой, пока она только ожидает сети/планировщика: статус карточки в таком случае «В очереди», а Pause всё равно доступна. При успешном принятии фоновой команды показывать Pause; при реальном отказе вернуть Play и пояснить ошибку.
2. Ввести единое для адаптеров состояние управления по `downloadId`: `PAUSED`, `STARTING`, `QUEUED`, `RUNNING`, `PAUSING`, `FAILED`, `FINISHED`, плюс `commandGeneration` для отсечения устаревших ответов. Это лишь UI-проекция над авторитетным сохранённым состоянием, не вторая база данных. `STARTING` и `PAUSING` НЕ должны самопроизвольно истекать с ложным успехом.
3. Кнопка, процент и прогресс не должны блокироваться полной перестройкой списка. Вынести маленький метод `renderControlState(id, state)` (или аналог), который обновляет только иконку, accessibility label и доступность действий. `refreshHeader` и event-based reload не должны затереть более новый `pendingCommand` старым снимком; сравнивать поколения/ревизии.
4. Запрос команды пересылать в ограниченную **фоновую очередь управления**, независимую от длинной очереди подготовки `reload`, `readRows`, обложек и SAF. Держать операции постановки/сохранения вне главного потока. Запуск Android Service и WorkManager вызывать из управляемого контекста; корректно выполнять требования foreground service (уведомление своевременно). Использовать application context и lifecycle-safe обработчики; отменять работу UI при закрытии экрана, не отменяя саму загрузку.
5. Для MangaLib: переходы сотен глав `paused→queued` записывать **одной пакетной операцией**, используя `putAll`/эквивалент и создавая WorkRequest без повторного чтения и сериализации всего списка на каждой главе. Сохранять порядок глав, устойчивое возобновление и существующую паузу сети 250 мс, не создавать дубли WorkManager.
6. Для RanobeLIB/Ranobes: пакетная фиксация, избегать повторных обходов и работы на UI; ставить команды в сериализованную очередь, сохранить логическое разделение произ­ведений при общей ограниченной сетевой очереди. Для Edge TTS: запись очереди и подготовка выбранного произведения вне UI; `QUEUED` считать успешно принятым состоянием для кнопки Pause, но не подменять реальный прогресс.
7. Для аудиокниг `DownloadWorker`: разнести командное состояние по `source/jobId`; если одна книга скачивается, Play другой должен **поставить её в очередь**, а не молча проигнорировать. Pause одной книги не должна устанавливать `halt` для чужой; активная загрузка остаётся единственной, если это существующее ограничение производительности. Восстанавливать очередь после перезапуска и сохранять уже скачанные главы.
8. После фактического подтверждения команды публиковать ровно одно событие `DownloadChangeBus.publish(id)` и точечно обновлять карточку; не делать `reload()` с фиксированной задержкой как единственный способ узнать о запуске. Допускается ограниченная фоновая сверка при восстановлении Activity/процесса и при исключениях, **без** постоянного поллинга и сканирования всей папки.
9. Защитить от быстрых нажатий Play→Pause→Play: обрабатывать команды последовательно с поколениями, не применять старое подтверждение к новому состоянию, не плодить одинаковые запросы и не забывать последнее намерение пользователя. Контекстные действия «Скачать всё», «Отмена», «В архив» работают предсказуемо вместе с Play/Pause.
10. Сохранить динамические цвета темы `UiColorScheme`, обычный фон кнопок, чёрные/контрастные иконки и все параметры доступности. Не менять UX других функций из-за одной оптимизации.

### 2.3. Критерии приёмки и тесты

- Сразу после Play иконка/надпись меняется **в следующий UI-кадр**; целевой ориентир до 100 мс на тестовом устройстве, без ожидания `reload()`.
- На большой манге (300–500 глав) main thread не выполняет JSON-сериализацию всех заданий и `SharedPreferences.commit`; во время запуска можно скроллить, нажимать кнопки и менять вкладки без ANR.
- В состоянии без сети или ожидания WorkManager кнопка доступна для Pause, статус **«В очереди / Ожидание сети»**, не выдаёт ложное «Скачивается».
- Play/ Pause/ Play при частых нажатиях: выполняется последнее действие, нет дублей задач и восстановленных неправильных иконок.
- Две аудиокниги: запуск B при активной A ставит B в очередь, не теряет команду; пауза B не останавливает A.
- Не теряются уже скачанные главы, MP3, WordBoundary, CBZ, HTML и SAF-права; восстановление после убийства процесса показывает фактическое состояние.
- Проверить все типы `AUDIO`, `MANGA`, `RANOBE`, `RANOBES`, `LINK`, `EDGE` в общем менеджере и их профильных экранах. Проверить `DownloadChangeBus`, состояние при `onResume` и корректное завершение загрузки/паузы.
- При сборке выполнить `:app:assembleRelease` в GitHub Actions, android instrumentation UI-тест на нажатие и смену пиктограммы и профилирование через Perfetto/StrictMode. **Сейчас тесты на устройстве не проводились.**

## 3. Адресные события глав и общий прогресс без полного обхода (P0, развитие Play/Pause)

**Запрос пользователя:** не заставлять одну кнопку Play/Pause ждать обновления сотен глав. При скачивании одной главы менять только её карточку и общий прогресс произведения; сохранять общий прогресс локально, не создавая лишних потоков и частой записи JSON. **Статус:** утверждаемая архитектура для реализации в v1.11.176, исходники v1.11.175 пока не изменяются.

### 3.1. Почему текущая система делает лишнюю работу

По исходному архиву `PROChitalka-v1.11.175-beta-CLEAN-GradleCompileHotfix-Full-Source.zip`:

- `DownloadChangeBus.publish(id)` уведомляет только об изменении **всего произведения**. `UnifiedDownloadManagerActivity.downloadListener` через 350 мс вызывает `reload()` целиком, который делает `DownloadsRepository.loadOne`, `readRows` (пересборка всех глав), `buildInfo`, запись двух снимков на диск и `adapter.submit(rows)`. При частых событиях это лишние O(N) операции.
- В `UnifiedDownloadManagerActivity.control()` после команды есть дополнительный `postDelayed(this::reload,450)`; запуск управления сцеплен с тяжёлым обновлением экрана.
- `DownloadWorker` уже посылает прогресс примерно раз в 600 мс, но `BookImportManager.put` периодически пересохраняет **все** задачи. `MangaLibStorage.liveProgress` уже использует полезный in-memory overlay, однако внешний bus всё равно содержит только ID книги.
- Менеджер аудиокниг при обновлении одной позиции перебирает список состояний, а менеджер Edge TTS для строк может снова получать `ChapterSnapshot` через SAF. Не запускать этот путь на каждом байте/странице.

### 3.2. Три независимых уровня: команда, прогресс, долговременное состояние

1. **DownloadCommandController** — Play/Pause/Cancel/Enqueue, немедленно отвечает UI состоянием `STARTING/QUEUED/PAUSING`; фактический запуск в существующих фоновых исполнителях. Команды сериализуются по `downloadId` с `commandGeneration`; не ожидать ни списка глав, ни SAF.
2. **DownloadProgressTracker** — лёгкая *проекция в памяти* для каждого `downloadId`: map `chapterId -> ChapterProgress`, агрегатные счётчики и последняя ревизия. Обновляется только событием от конкретного worker, без чтения файлов или рефетча списка. Это не дополнительный источник истины о завершении глав.
3. **DownloadProgressStore** — маленький долговременный снимок **общего** прогресса по книге (и метаданные активной главы) в приватном `AtomicFile` JSON. Долговечные статусы глав остаются в действующих хранилищах загрузчиков и, для Edge TTS, в зафиксированном SAF-индексе. Не создавать полную вторую JSON-копию списка глав при каждом изменении процентов.

Разделить события: `COMMAND_STATE`, `CHAPTER_PROGRESS`, `CHAPTER_COMMITTED`, `BOOK_PLAN_CHANGED`, `ERROR`, `RESET`. Расширить `DownloadChangeBus` новым типизированным каналом, **сохранив совместимость** прежнего `publish(id)` для редких структурных событий и старых слушателей. Все события должны содержать `downloadId`, `chapterId` (если применимо), `generation/sequence` и краткую текущую информацию, а не массив всех глав. Один общий coalescing scheduler, не Handler/Thread на каждую главу.

### 3.3. O(1) изменение общего прогресса

При открытии/изменении состава очереди **один раз** вычислять `denominator = sum(weight_i)` и `numerator = sum(weight_i * fraction_i)`, где `fraction_i` от 0 до 1, а `weight_i` — фиксированный вес главы в данной очереди; по умолчанию `1`. Допускаются известные стабильные веса (например, объём текста/число слов Edge TTS), если они известны **до начала** расчёта. В обычном интерфейсе можно показывать отдельно «Готово глав X из N» и «Общий прогресс Y%». Не смешивать метрики отдельных источников без определения общего плана.

При событии главы `i` с новым `fraction_i'` менять **только вклад этой главы**:

`numerator' = numerator + weight_i * (fraction_i' - fraction_i)`;
`overallPercent = clamp(100 * numerator' / denominator, 0, 100)`.

Если вес или состав очереди меняется, обновить агрегат **однократно по событию `BOOK_PLAN_CHANGED`**. Прогресс хранить внутренне в целых тысячных/базисных пунктах, чтобы избежать ошибок округления; пересчёт полного списка не делать в каждом progress callback. Нужны `completedChapters`, `downloadedBytes`, `activeChapter` и `running/queued/paused` отдельно.

Для каждого типа сохранять точный смысл единиц: `AUDIO`/`LINK` — байты, если известен стабильный total, иначе прогресс отдельного файла; `MANGA` — подтверждённые страницы в главе / известное число страниц; `RANOBE/RANOBES` — этапы записи и подтверждённые завершённые главы; `EDGE` — покрытие сегментами/словами и окончательное подтверждение SAF-индекса. При неизвестном `total` показывать неопределённый прогресс и количество готовых глав, **не выдумывать проценты**. 100% отдельной главы и книги — только после устойчивого commit результата (MP3/CBZ/HTML/index), не по достижению 100% сетевого приёма.

**Идемпотентность:** обработчик хранит `lastSequence` и старый вклад `chapterId`; повторный или запоздавший callback не добавляет прогресс второй раз. `generation` для нового запуска/сброса, `sequence` для упорядочения. Перезапуск загрузки может уменьшить процент только по осмысленному событию сброса, не вследствие устаревшего снимка.

### 3.4. Обновление только двух визуальных элементов

В открытом менеджере **один** `CHAPTER_PROGRESS` обновляет:

- Только строку активной главы через `RecyclerView.Adapter.notifyItemChanged(position, PAYLOAD_PROGRESS)` либо эквивалент, без замены списка, пересоздания кнопок или чтения `DocumentFile`. Использовать стабильный ID главы и индекс `chapterId -> adapterPosition` (перестраивается только при изменении состава/сортировки).
- Только верхний `ProgressBar`, проценты, счётчик готовых глав и при необходимости скорость/статус. Не трогать название, обложку, `Info` и значения других глав.

Отдельный `CHAPTER_COMMITTED` дополнительно обновляет галочку/статус именно этой главы, `completedChapters` и общий прогресс. `BOOK_PLAN_CHANGED` допускает разовую фоновую пересборку списка и `DiffUtil`, но не по таймеру. `Info` и проверку SAF выполнять только при открытии вкладки/смене папки/ошибке, а не на каждый chunk.

**Частота событий:** скачивающий worker может часто получать байты/страницы, но UI-события объединяются по `downloadId + chapterId`. Для видимого экрана целевой максимум около **4–5 обновлений/с** на активную главу (одно каждые 200–250 мс, немедленно — смена состояния/завершение/ошибка/нажатие). Если экран не видим, обычные UI-события не гонять; при `onResume` получить последнее состояние из in-memory cache и при необходимости один раз сверить ревизию. Foreground notification обновлять отдельно, с меньшей частотой (например, раз в 1–2 с), кроме финального события. Не создавать по таймеру фоновый полный аудит папок. Эти интервалы — начальные ориентиры, корректируются по профилированию.

### 3.5. Локальный JSON прогресса — малый и безопасный

**Кэш — не второй архив файлов.** Например `filesDir/download_progress_v176/<bookKey>.json`, сохранять компактный снимок вида:

```json
{
  "schema": 1,
  "downloadId": "audio:example",
  "revision": 42,
  "plannedChapters": 120,
  "completedChapters": 37,
  "weightedDone": 3750,
  "weightedTotal": 12000,
  "downloadedBytes": 91827364,
  "activeChapterId": "chapter-38",
  "activeProgress": 48,
  "state": "RUNNING",
  "updatedAt": 1794920000000
}
```

`weightedDone/weightedTotal` в примере условны (масштаб фиксированных единиц), не должны восприниматься как независимый реестр завершения глав. При необходимости `activeChapterId` может быть null. Не включать в этот JSON полные MP3/WordBoundary, оглавление, тысячи файлов или `JSONArray` всех задач.

- Хранить текущее состояние в памяти; JSON записывать **пакетно** в одном ограниченном IO executor по dirty-флагу с дебаунсом примерно 3–5 с **только во время изменений**; никогда не писать из UI и не делать `SharedPreferences.commit()` на каждом chunk.
- Немедленно сбрасывать контрольную точку на фоне при `CHAPTER_COMMITTED`, `PAUSE`, `CANCEL`, `FAILED` и завершении книги. До появления 100% обязательным остаётся успешный commit реального файла/индекса; кэш-снимок не должен подменять его.
- Использовать Android `AtomicFile` или эквивалент атомарной замены, версионировать схему и использовать ключ, отличающий книгу и источник (включая очереди по разным папкам). Для SAF-файлов хранить ссылки/индексы в существующих источниках, не в UI-кэше.
- При запуске мгновенно показать последний снимок как **предварительный**, затем **один раз** сверить его с авторитетным хранилищем, если ревизия/путь/схема изменились, был аварийный выход или не удалось подтвердить завершение. Не запускать хеширование сотен MP3 при каждом открытии; проверять спорные или незавершённые записи адресно.
- После аварийного завершения допускается потеря нескольких секунд промежуточного визуального процента, но не готовых файлов, не флагов «готово», не команды Pause и не сохранённой очереди.

### 3.6. Источники изменений: одна запись и одно событие

Workers `DownloadWorker`, `EdgeFullBookService`, `MangaLibDownloadWorker`, `RanobeLibDownloadWorker`, `RanobesDownloadWorker`, `DirectLinkDownloadService` отправляют `CHAPTER_PROGRESS(bookId,chapterId,done,total,bytes,state,sequence)` в общий трекер без ожидания диска. При записи очереди не пересериализовать весь список глав на каждой странице, не выполнять лишний SAF-обход. У MangaLib сохранить существующий live-overlay, подключить его к адресным событиям вместо повторного чтения всех глав. Существующий `DownloadChangeBus.publish(bookId)` продолжает обслуживать изменения структуры и совместимость.

Если сервис живёт в отдельном процессе, локальный in-memory bus не подходит как единственный транспорт: добавить межпроцессную доставку или чтение сохранённой версии при возвращении экрана. Не запускать фоновую службу только ради отображения процентов.

### 3.7. Очередь без лишних потоков, защита управления

- Для управления Play/Pause — **одна ограниченная последовательная очередь команд**, не связанная с выполнением тяжелого `reload`; сетевые workers продолжают использовать существующий WorkManager/Foreground Service. Не создавать executor на каждую главу.
- Для записи компактного JSON — один сериализованный исполнитель/очередь с коалесцированием по книге, максимум один ожидающий flush на книгу. При быстрых событиях обновлять последнюю запись, а не добавлять в очередь 200 операций.
- `PLAY` меняет UI сразу на `STARTING`, затем подтверждение — `QUEUED/RUNNING`; `PAUSE` меняет сразу на `PAUSING`, затем подтверждение — `PAUSED`. Старые события не перетирают новое намерение по `commandGeneration`. При отсутствии сети статус «В очереди / Ожидание сети»; Pause доступна.
- Не читать SAF и не пересоздавать хранилища при каждом изменении прогресса. При `onPause/onDestroy` отписывать UI-подписчика, но загрузка и фиксирование progress/checkpoint продолжаются.

### 3.8. Приёмка и измерения

1. Книга с **500 главами**: при скачивании одной обновляются ровно одна видимая строка и общий прогресс; повторных `readRows()` и `adapter.submit()` на каждый chunk нет. После выхода и возврата данные совпадают с устойчивым источником.
2. Книга с 1000 фрагментов Edge TTS: прогресс учитывает только готовые сегменты; только после commit главы появляется галочка, 100% не возникает на 99% стадии публикации.
3. 1000 callbacks прогресса подряд: не создаются 1000 IO-записей/перерисовок. Проверить верхние границы частоты UI и checkpoint.
4. Play/Pause/Play, смена вкладки, уход приложения в фон, повторное открытие, убийство процесса, отключение сети, плохой SAF, смена папки, две книги в очереди: нет дублей, устаревших процентов, пауз не того задания и ложных 100%.
5. Во время активной загрузки быстрый скроллинг списка остаётся плавным; сборки debug/release измеряются в Perfetto/StrictMode, а `:app:assembleRelease` обязательно запускается в GitHub Actions.
6. Сравнить с v1.11.175 счётчики `reload`, `readRows`, SAF-вызовов, JSON-коммитов, перерисовок строк и время до реакции Play. Метрики только debug, без постоянного логирования каждого байта в release.

**Приоритет:** P0 — адресные события/агрегат/UI и немедленная реакция Play; P1 — атомарный summary cache, пакетная запись, восстановление и оптимизация всех источников. Новая схема не отменяет сохранность и существующие гарантии записи.

## А. Аудит v1.11.174 — проверенные участки кода

### А1. Комиксы и манга — сбой определения последней страницы, режим «Лента» (P0)

**Подтверждённый дефект алгоритма:** `ComicReaderActivity.java:399–402` вычисляет текущую картинку так: перебирает `img.offsetTop` и оставляет **последнюю** картинку, чей `offsetTop` не превышает `window.scrollY + 0.25 * innerHeight`. При этом `renderCurrentAssets()` (`:392–396`) создаёт все `<img loading='lazy'>` **без зарезервированных размеров**; в режиме ленты применяется `height:auto`. Пока изображения не загружены и их высота не определена, несколько `offsetTop` способны совпадать (в частности быть равными нулю). Даже при нахождении в начале документа алгоритм может сообщить индекс последней страницы. Моделирование с одинаковыми нулевыми `offsetTop` для 3/30/120 элементов возвращает соответственно индексы 2/29/119. Это кодовая причина ошибочного *определения* позиции, а наблюдаемый физический прыжок может дополнительно зависеть от `restore` и загрузки изображений.

**Усиливающие факторы:**
- `:405–414`: `restoreWhenReady()` в ленте переводит в `loading='eager'` **все изображения от начала до `n`**, ожидает их завершения до 6,5 с и дважды вызывает `restore()`; при ложном `n=last` это резко увеличивает объём I/O. Даже после возврата к выбранной позиции загрузка изображений выше её изменяет высоты и вызывает layout shift.
- `:342–347`: один и тот же WebView каждый раз загружает новый HTML; WebView скрывается через `setAlpha(0f)` и затем принудительно появляется (`:336`, `:344–346`), что даёт видимый blank/flash при переключении глав/режимов. Fallback в 10 с способен показать ещё неустоявшуюся геометрию.
- `:46–61`: позиция опрашивается каждые 600 мс, и ошибочно вычисленная страница записывается в `comic.page` / `ChteicoStore.recordComicPage()`; тем самым ложный «последний номер» может закрепиться в истории.
- `:330,355–387`: общий изменяемый `currentAssets` очищается и заполняется фоновой работой; проверка `generation` производится перед `loadDataWithBaseURL()`, но не защищает все операции подготовки ресурсов в фоновых потоках.
- `:181–190,309–310`: каждая WebView-загрузка через `shouldInterceptRequest()` может заново получить SAF-дерево, пройти `findFile()` для компонентов пути и вызвать `getType()`; большое число картинок создаёт цепочку медленных провайдерных операций.

**Вывод:** дефект расчёта страницы подтверждён исходниками. Масштаб мерцания, точную частоту рывков и вклад SAF предстоит измерить на реальных устройствах.

## P0 — уже выявленные блокирующие причины

### P0.1. Edge TTS: полное восстановление готовой книги перед запуском

- **Код:** `EdgeStreamingService.java:425–447` — в фоне подготавливает книгу, но синхронно по отношению к `bookReady` вызывает `EdgeChapterArchive.restore()`; первая готовая озвучка зависит от восстановления всей книги.
- **Код:** `EdgeChapterArchive.java:485–537` — `restoreChapter(...,-1)` обходит **все** каталоги глав через SAF, `findFile()` каждого фрагмента, `digest(to)` для существующего MP3 и заново копирует WordBoundary независимо от существующей локальной копии.
- **Последствие:** для полностью подготовленной книги с сотнями/тысячами отдельных MP3-фрагментов время запуска растёт с числом файлов и задержкой провайдера SAF; повторные чтения/копирования могут блокировать очередь `io`.
- **ТЗ:** убрать `restore()` из критического пути `openBook()`. Сначала открыть локальный индекс/текущий фрагмент и дать доступ к озвучиванию; при cache miss адресно подгружать **текущий**, затем 1–2 следующие фрагмента в фоне. Восстановление всей книги — только по отдельному явному действию, без блокировки UI. Не копировать сохранённый WordBoundary и не хешировать каждый неизменный локальный MP3 на каждом открытии. Проверки при первоначальной записи, подтверждённом повреждении и смене ревизии сохранить.
- **Инварианты:** синхронизация WordBoundary, последовательность сегментов, старые главы merged, точное возобновление, пауза, отсутствие повторного синтеза, отсутствие ложной готовности и сохранение живых задач.

### P0.2. Выбор папки книг: синхронный SAF-пробник на UI-потоке

- **Код:** `DownloadFolderPicker.java:155–198` — метод `receive()` выполняет `verifyWritable()` непосредственно в обработчике результата `Activity`, включая create/write/read/delete и затем `SharedPreferences.commit()`.
- **Последствие:** slow SAF/SD/облако может замораживать UI; пересоздание настроек после выбора может дополнительно увеличить задержку.
- **ТЗ:** перенести файловый пробник в `ExecutorService`, показывать неблокирующий статус «Проверка доступа», не пересоздавать весь экран до окончания; сохранить прежний URI до успеха, а при ошибке оставить старый путь и показать точную причину. Persistable permission сохранять корректно; разрешения прежней папки не отзывать автоматически. **Новая папка не равна переносу старых файлов**: до явно подтверждённой миграции старые главы остаются доступны по прежнему URI. Не проверять новые каталоги при каждом открытии настроек.

## P1 — подтверждённые дорогие операции вне Edge TTS

### P1.1. Манга/комиксы: работа с архивом на главном потоке при открытии

- **Код:** `ComicReaderActivity.java:69–76` — `ComicLibrary.chapters()` вызывается внутри `onCreate()` на UI-потоке.
- **Код:** `ComicLibrary.java:122–156,186–204,224–239` — построение каталога может вызвать `DocumentFile.listFiles()` и обход подпапок, для CBZ/CBR — `ensureArchiveExtracted()`, копирование архива из SAF, распаковку и сортировку страниц.
- **Риск:** первая отрисовка экрана может долго ждать чтения/извлечения большого архива. `ComicReaderActivity.loadChapter()` уже использует поток (`:325–340`) — проблема именно в начальном `chapters()`.
- **ТЗ:** сначала рисовать оболочку/прогресс открытия, затем строить оглавление и индекс страниц на отдельном executor; кэшировать метаданные по URI + размеру + mtime/ревизии. Извлечение только открываемой главы — фоновое. Сохранить текущую главу, страницу, ориентацию и поведение WebView.

### P1.2. Менеджер загрузок MangaLib: полная перерисовка по таймеру

- **Код:** `MangaLibChapterDownloadsActivity.java:24–32,90–159` — каждые 2500 мс вызывается `drawStatus()` на UI-потоке. Метод загружает все задания из JSON, `entries.removeAllViews()` и пересоздаёт все карточки; для каждого нового тома снова проходит по `items` (`:115–124`), что даёт повторяющиеся проходы при многих томах.
- **ТЗ:** `RecyclerView + DiffUtil`/эквивалент точечного изменения, группы томов и агрегаты считать однократно (`O(N)`), данные вычислять в фоне, затем менять только затронутую главу и счётчики. Обновления принимать через `DownloadChangeBus`/WorkManager и объединять по 250–400 мс; не перестраивать экран по таймеру, если нет изменений. Сохранить позицию прокрутки и действия карт.

### P1.3. Загрузка MangaLib: синхронное сохранение полного списка после каждой страницы

- **Код:** `MangaLibDownloadWorker.java:162–178` — после каждого изображения вызывается `MangaLibStorage.put(ctx,job)`, затем фиксированная `Thread.sleep(250)`.
- **Код:** `MangaLibStorage.java:31–61` — `put()` перечитывает полный массив заданий, сериализует **все** задания в JSON, выполняет синхронный `.commit()` и уведомляет слушателей.
- **Риск:** большая серия/длинная глава получает многократные перепаковки JSON и синхронные записи. Отдельная фиксированная пауза добавляет минимум 0,25 с на страницу (например, 100 страниц — 25 с сверх передачи), но может служить защитой от rate limit.
- **ТЗ:** хранить рабочие счётчики в памяти и отправлять визуальный прогресс событиями; durable checkpoint выполнять пакетно по времени/количеству страниц **и обязательно** при pause/fail/complete/остановке процесса и на безопасных границах. При принудительном завершении не терять уже загруженные страницы, которые и так остаются на диске. Пауза между сетевыми запросами — отдельно оценить по 429/скорости/условиям сервиса; **не отключать вслепую**.

### P1.4. Общий менеджер загрузок: повторный SAF-обход архива глав

- **Код:** `DownloadsRepository.java:282–336` — при построении списка Edge перебирает локальные `book.json`, задания и `EdgeChapterArchive.savedBooks(ctx)` с обходом SAF-каталога; `fromEdge()` (`:92–113`) при готовности вызывает `EdgeChapterArchive.snapshot()`.
- **Код:** `EdgeChapterArchive.java:46–66` — snapshot кэшируется на 9 секунд, после чего снова обходит папки и индексы; `UnifiedDownloadManagerActivity.java:207–236,289–307` перезапрашивает его при reload.
- **Состояние:** начальные сканирования в `DownloadActivity`/`UnifiedDownloadManagerActivity` в основном вынесены в executor — не утверждаем, что они напрямую блокируют UI. Однако они занимают дисковую/SAF-очередь и повышают задержку обновления карточек, особенно при множестве книг.
- **ТЗ:** сохранить отдельную лёгкую persistent-карту `{bookId, chapterId, state, fileUri, revision}` после успешной записи/удаления. `loadOne(id)` по возможности должен читать только данный ID, без полной инвентаризации SAF; полный SAF-обход выполнять при первой миграции, ручном обновлении или реальном invalidation, а не циклически по TTL. Экраны должны получать событийные изменения, с устойчивой обработкой внешнего удаления/потери разрешений.

## 1. Edge TTS: больше не объединять аудиофрагменты при озвучивании/скачивании

### 1.1. Принцип

- Каждый законченный фрагмент озвучивания сохраняется как **самостоятельный MP3**.
- Для каждого фрагмента сохраняется необходимая собственная информация WordBoundary для синхронизации текста. Разметка сохраняется только в исходных данных Edge TTS и **не теряется**.
- Считаем главу готовой только после того, как все её необходимые фрагменты и данные для воспроизведения успешно сохранены и индекс главы зафиксирован; **не требуется единый MP3 главы**.
- Сохранение строго адресное, только для выбранной главы. Без объединения MP3-кадров, обязательного rename `.pending`, повторного чтения всех MP3 и пересканирования остальных глав.
- Повторное сохранение использует готовые аудиофрагменты, не запускает озвучивание снова, если данные доступны.
- Воспроизведение в ReaderActivity/Edge TTS должно переходить между фрагментами в правильном порядке, сохраняя подсветку текста, позицию, паузу/возобновление и прогресс.
- Необратимое удаление данных после публикации запрещено; старые готовые главы остаются читаемыми.

### 1.2. Обязательные изменения кода при будущей реализации

- `EdgeFullBookService.java`: всегда использовать адресную публикацию фрагментов `publishFragmentsOne(...)` или эквивалент. Полностью убрать вызов `autoMerge()` для выбора пути обычной загрузки.

## 2. Контекстное меню загрузки: экспорт в отдельную папку книги с MP3-файлами глав

### 2.1. Новый пункт

**Точное название в контекстном меню карточки Edge TTS:**

> Перенести готовые аудиоглавы едиными файлами в аудиотеку

Расположение: кнопка `⋮` карточки произведения на экране «Загрузки», только для типа `EDGE`. Существующий пункт «Перенести в аудиокниги» заменить новым, а не создавать два дублирующих действия.

**Утверждённое правило: ОДНА ЗАВЕРШЁННАЯ ГЛАВА = ОДИН САМОСТОЯТЕЛЬНЫЙ MP3.** Экспортировать книгу **одной папкой с названием произведения**, а внутри хранить отдельные MP3 глав и **одну** общую обложку `cover`. Разные главы никогда не объединять в единый MP3 всей книги. Слово «едиными» в названии команды означает единый MP3 **каждой главы**, а не один файл всей аудиокниги.

**Структура результата (пример):**

```text
Аудиотека/
  Название книги/
    cover.jpg
    001 - Глава 1. Начало.mp3
    002 - Глава 2. Продолжение.mp3
    004 - Глава 4. Финал.mp3
```

Если оглавления и достоверных названий глав нет, вместо вымышленных названий используется простая нумерация: `Глава 001.mp3`, `Глава 002.mp3`, ... . Реальное расширение `cover` определяется форматом доступной обложки (`cover.jpg`, `cover.png` и т. п.); создавать только один файл обложки.

### 2.2. Значение операции

- Экспортировать **каждую готовую главу отдельным MP3-файлом**. Внутри одной главы разрешено соединить её ранее сохранённые Edge TTS-фрагменты в один итоговый файл главы, **только после явного выбора этой команды**. Между главами объединения не выполняются.
- **Целевая папка:** `Аудиотека/<Название книги>/`, где `<Название книги>` — реальный заголовок произведения. Папка создаётся/находится один раз и повторно используется при экспорте новых завершённых глав. Нельзя раскладывать главы разных произведений в одну папку. Если название книги недоступно, использовать устойчивое безопасное имя по идентификатору книги, а не случайное имя.
- **Имена MP3:** при наличии оглавления использовать точное книжное название соответствующей главы, по возможности с числовым префиксом исходного порядка для правильной сортировки: `001 - Глава 1. Начало.mp3`. Не заменять известный заголовок шаблоном «Глава N». Если оглавления нет — `Глава 001.mp3`, `Глава 002.mp3` и т. д. Для частичного экспорта сохранять исходные номера (например, главы 1, 2 и 4, не перенумеровывать их как 1, 2 и 3).
- Нормализовать только недопустимые символы имени SAF/файловой системы, пробелы по краям и излишнюю длину; не менять осмысленный текст названия. Коллизии одинаковых заголовков разрешать исходным номером или устойчивым идентификатором главы; фактические URI и имена сохранять в индексе аудиотеки. Не создавать `Аудиокнига.mp3` из всех глав и не экспортировать MP3 по одному на исходный фрагмент.
- В аудиотеке зарегистрировать **одно произведение с отдельными треками-главами**, расположенными по исходному порядку оглавления. Один готовый экспортируемый MP3 соответствует одному треку/одной главе. Названия глав отображать отдельно, воспроизведение следующей главы должно работать стандартным порядком аудиотеки.
- В экспортируемые файлы **не включать WordBoundary/JSON** и не создавать рядом служебные WordBoundary-файлы. Исходная разметка WordBoundary в Edge TTS **остаётся на месте** для чтения и подсветки текста.
- **Обложка одна на книгу:** сохранять в папке произведения **ровно один** `cover.jpg` / `cover.png` (в зависимости от исходного формата). Использовать эту общую обложку **только для отображения произведения в карточке аудиотеки/программы**. **Не встраивать обложку в MP3 глав (без ID3 APIC)**, не создавать отдельные копии обложки рядом с каждой главой и не повторять её в отдельных файлах.
- При повторном экспорте использовать уже сохранённый `cover`, не перезаписывать его без необходимости. Метаданные карточки аудиотеки должны ссылаться на общий URI обложки папки книги. При отсутствии исходной обложки — предложить выбрать/восстановить её, не создавать случайную обложку и не инициировать скрытую сетевую загрузку.
- Указать в тегах MP3 при наличии данных: `title` = название конкретной главы, `album` = название произведения, `artist` = автор/исполнитель, `track` = исходный порядковый номер главы; длительность MP3 должна корректно определяться плеерами.
- Исходные MP3-фрагменты, WordBoundary и индексы Edge TTS **не удалять и не перезаписывать**. «Перенести» здесь означает создать копии глав для аудиотеки. Загрузка и обычное воспроизведение Edge TTS по-прежнему работают на отдельных фрагментах и WordBoundary; пункт 1 ТЗ не меняется.
- Старые готовые главы, уже хранящиеся единым MP3, экспортировать как **отдельный трек главы** без повторного обязательного объединения; при необходимости перенести/добавить метаданные **только** в копии для аудиотеки, без встраивания обложки в MP3.

### 2.3. Если книга подготовлена не полностью

- Действие доступно при наличии хотя бы одной **полностью готовой** главы, даже если вся книга ещё не скачана.
- В диалоге показать «Готово N из M глав». Если готовы не все, предложить «Экспортировать готовые главы» либо «Отмена». Создавать MP3 **по одному на каждую готовую главу**, пропуская все незавершённые главы; не создавать частичные MP3 для незавершённых глав.
- Если нет ни одной готовой главы, действие недоступно с понятным пояснением.
- Повторный экспорт после появления новых глав не должен создавать дубликаты уже экспортированных глав; существующие готовые треки сохранять. Повторное создание изменившейся главы — только с защитой её прежней готовой копии до успешной фиксации новой.

### 2.4. Производительность и надёжность

- Обрабатывать **по одной главе за раз**; потоково читать только её исходные фрагменты и записывать один выходной MP3 главы, не загружая целую главу или книгу в оперативную память. Объединение выполняется **только в режиме экспорта**, а не в процессе скачивания Edge TTS.
- Не копировать промежуточные ID3/Xing/VBR-заголовки исходных MP3-фрагментов как обычные аудиокадры; обеспечивать правильную длительность и совместимость параметров внутри **каждой главы**. При несовместимости параметров исправлять только экспортируемую копию конкретной главы, не источники.
- Выполнять экспорт в фоне, показывать прогресс по главам и возможность отменить операцию; отсутствие экспорта не блокирует синтез и обычные загрузки Edge TTS. Не добавлять периодических проверок и полного сканирования книги.
- Через SAF создавать/использовать **одну папку произведения** и новый документ для каждого MP3 главы. Сохранять фактический URI и имя папки, обложки и файлов глав; регистрировать трек в аудиотеке **только после** закрытия потока и успешной фиксации записи. При отказе показать конкретную главу и этап сбоя; не удалять исходники или ранее готовые треки и не помечать неполную запись успешной.
- Карточка аудиокниги должна ссылаться на папку произведения и общий `cover`; список треков составляется из отдельных MP3 глав в порядке исходного оглавления (либо по номеру без оглавления). Для повторного экспорта новых глав — добавлять их в ту же папку, не дублируя уже завершённые аудиотреки.
- Источник `cover` — локально доступное изображение произведения. Если его нет, предложить выбор/восстановление обложки без скрытой обязательной сетевой загрузки. Хранить только одну копию в папке книги, не в каждом MP3.

## 1. Edge TTS — быстрое и надёжное завершение главы без ошибки на 99%

### Исходная проблема
В текущей версии после завершения генерации аудио возможно сообщение «Не удалось записать завершённую главу в выбранную папку Edge TTS», при этом прогресс остаётся на 99%. Сравнение v1.11.154–157 с v1.11.171 выявило добавленную после v157 повторную SHA-256-проверку MP3, изменения выбора папки и унаследованную общую публикацию готовых глав вместо строго адресной операции. Это возможные причины, но точная ошибка конкретного файлового провайдера без журнала Android не установлена.

### Реализация
1. Публиковать *только выбранную главу* (`publishOne` либо равнозначная адресная операция); ошибка другой главы не влияет на выбранную.
2. Использовать однократную потоковую запись итогового MP3 через Android SAF, без обязательной пары `.pending` + `renameTo` и без повторного чтения MP3 для SHA-256 после каждой записи.
3. Создавать новый документ с уникальным именем, использовать его фактический `Uri` (даже если SAF-провайдер скорректировал имя); не удалять прежний работоспособный MP3 до успешного завершения замены и обновления индекса.

### Подтверждённые места в текущем коде v1.11.171

Встроенный `ItemTouchHelper` рассчитан на завершённый swipe-to-dismiss: после срабатывания `onSwiped()` он сохраняет ссылку на смахнутый ViewHolder до отсоединения от `RecyclerView`. Фактический перехват `MotionEvent` пока не подтверждён тестом на устройстве.

1. Реализовать частичный свайп **для раскрытия действий**, а не успешный полный свайп удаления. Предпочтительно отдельная распознающая логика горизонтального жеста для переднего слоя карточки; при завершении фиксировать его в точке `+actionsWidth`.

3. После раскрытия передняя карточка не перекрывает область «В архив» и «Отмена». Обе кнопки имеют нормальные touch-targets (не менее 48dp по высоте) и отдельные `OnClickListener`.

## 3. Усталость: пороги и действие

| Редкость | Обычная особь: порог шкалы | Мерцающая особь: порог шкалы |
|---|---:|---:|
| Обычная | 90% | 85% |
| Необычная | 80% | 75% |
| Редкая | 70% | 65% |
| Легендарная | 65% | 60% |
| Мифическая | 60% | 55% |

Обозначим `P` — текущий прогресс шкалы в долях от 0 до 1; `r` — редкость 0…4; `s` — признак мерцания (0/1).

```
F_base = [0.90, 0.80, 0.70, 0.65, 0.60]
F = F_base[r] - (s ? 0.05 : 0.00)
```

При `P >= F` рыба становится уставшей. Скорость её перемещения уменьшается на **30%**: `V = V_base * 0.70`. Рывки после смены направления, включая касание границы, отключены: `turnBoost = 1.0`. Рыба продолжает плавать и разворачиваться.

### 3.1. Новая временная система (заменяет «навсегда»)

У состояния три значения:

- **FULL_STRENGTH** — рыба полна сил; движение и ускорение при повороте обычные; значок скрыт.
- **TIRED** — рыба устала; скорость ×0,70, поворотного ускорения нет; над рыбой виден индикатор с полной окружностью.
- **RECOVERING** — прогресс упал ниже `F`, рыба *всё ещё уставшая*, но идёт круговой обратный отсчёт до восстановления; скорость по-прежнему ×0,70 и без ускорения на поворотах.

Переходы:

| Откуда | Условие | Куда | Действие |
|---|---|---|---|
| FULL_STRENGTH | `P >= F` | TIRED | Сразу применить дебафф, показать иконку и полное кольцо |
| TIRED | `P < F` | RECOVERING | Начать обратный отсчёт с полного времени выбранной удочки |
| RECOVERING | `P >= F` до истечения | TIRED | Сбросить отсчёт; дебафф сохраняется |
| RECOVERING | `timeRemaining <= 0` и `P < F` | FULL_STRENGTH | Вернуть скорость и рывки; убрать значок и кольцо; можно кратко показать визуальный эффект восстановления |
| Любое состояние | Рыба сорвалась / поймана / новая попытка | FULL_STRENGTH | Удалить таймер, сбросить временное состояние |

**Пограничное правило:** ровно на пороге `P == F` рыба считается уставшей, а не восстанавливающейся. Таймер запускается только при `P < F`. Если во время обратного отсчёта прогресс вернулся хотя бы к порогу, отсчёт сбрасывается целиком, а не ставится на паузу. Следующий уход ниже порога запускает новое полное время.

Таймер не должен истекать, пока игра поставлена на паузу, приложение свёрнуто либо экран рыбалки остановлен. Использовать игровое время / ограниченный `dt`, не абсолютное календарное время. Состояние старой обложки (случайная находка) не наследует усталость рыбы.

### 3.2. Время восстановления для каждой удочки

Пользователь указал «для тренировочной 2 секунды и +2 за каждую редкость» одновременно с «время будет для каждой удочки своё». Для формализации ТЗ **+2 с интерпретировано как каждый следующий уровень удочки**. Это единственный пункт, где возможна альтернативная трактовка слова «редкость» (редкость рыбы вместо класса удочки); при необходимости время можно уточнить отдельно, не затрагивая остальную логику.

| Удочка | Индекс `rod` | Время восстановления (если ниже порога) |
|---|---:|---:|
| Тренировочная | 0 | 2 с |
| Новичка | 1 | 4 с |
| Хорошая | 2 | 6 с |
| Мастера | 3 | 8 с |
| Прочитателя | 4 | 10 с |

Формулы:

```
recoverySeconds = 2 + 2 * rod
remaining = max(0, remaining - deltaSeconds)  // только RECOVERING и P < F
ringFraction = remaining / recoverySeconds
```

Чем выше удочка, тем дольше сохраняется замедление рыбы, когда прогресс упал ниже порога. Круговая шкала идёт от 100% к 0%, потом исчезает вместе со значком при восстановлении сил. В состоянии TIRED окружность остаётся полностью заполненной без обратного отсчёта.

## 4. Иконка дебаффа скорости и круговой таймер

**Одно графическое обозначение:** контурный разветвлённый **хвост рыбы** + две нисходящие стрелки/шеврона. Не рисовать целую рыбу, крылышко, перо, лицо или сложную сцену. Символ должен узнаваемо означать «рыба движется медленнее».

Ресурс Android: `app/src/main/res/drawable/ic_fishing_fatigue_debuff.xml`; тип `VectorDrawable`, размер 32×32 dp и `viewport` 32×32, прозрачный фон. Чёрный контур в XML служит базой, в приложении **обязательно перекрашивать через палитру текущей темы**; на тёмной теме не оставлять чёрный значок на тёмном фоне. Не вводить фиксированную цветовую тему.

**Расположение:** поверх шкалы вываживания, у плавающей рыбы, по центру над её текущей визуальной позицией с небольшим отступом; позицию обновлять на каждом игровом кадре. Символ **не вращать** с направлением спрайта рыбы: рыба может смотреть вверх или вниз, хвост с шевронами на индикаторе всегда ориентирован нормально. При близости к границе экрана ограничивать координаты, не обрезать таймер и не закрывать основные элементы управления.

**Анимация:** стиль кругового таймера как у существующей анимации подсечки (плавное кольцо), но длительность динамическая по удочке. В центре постоянно один и тот же `VectorDrawable`; кольцо вокруг него рисуется независимо (Canvas `drawArc` / специализированный View), чтобы можно было отображать точно `remaining / recoverySeconds`, а не полагаться на фиксированную длительность XML-анимации подсечки. При возврате прогресса к порогу — заполнить кольцо обратно и прекратить обратный отсчёт. При восстановлении сил — плавно скрыть индикатор без дополнительных всплывающих диалогов.

## 5. Вероятности редкости в зависимости от удочки

### 5.1. Утверждённые проценты при качестве заброса «Хорошо»

| Удочка | Обычная | Необычная | Редкая | Легендарная | Мифическая | Цена, золото |
|---|---:|---:|---:|---:|---:|---:|
| Тренировочная | 87,80% | 12,20% | 0% | 0% | 0% | 0 |
| Новичка | 60% | 16% | 10% | 8% | 6% | 180 |
| Хорошая | 59,76% | 24,39% | 15,85% | 0% | 0% | 800 |
| Мастера | 36% | 24% | 18% | 12% | 10% | 3 000 |
| Прочитателя | 26% | 25% | 21% | 16% | 12% | 8 000 |

**Строгие запреты:**

- Тренировочная удочка: **ни редкой, ни легендарной, ни мифической** рыбы.
- Хорошая удочка: **ни легендарной, ни мифической** рыбы.
- Для новичка, мастера и прочитателя остальные утверждённые вероятности сохраняются буквально. В частности, у новичка есть шанс легендарной и мифической рыбы, хотя у хорошей удочки он равен нулю. **Не исправлять эту асимметрию без нового указания.**

Запрещённые проценты перераспределяются среди разрешённых редкостей пропорционально их исходным весам:

```
P_final(rarity i) = 100 * P_base(i) / sum(P_base(k) for k in ALLOWED_rod)
```

Поэтому для тренировочной удочки необычная рыба имеет **12,20% после перенормировки**. Это специальное следствие утверждённой таблицы, даже если до нормировки её ограничение составляло 10%.

### 5.2. Вероятности для более редких рыб

Базовое предложение: для первой редкости выше класса удочки — не более 10%, для каждой следующей ступени — на 2 процентных пункта меньше: `C(d)=max(0, 10-2*(d-1))%`, где `d>=1`. Применять **только там, где нет более конкретного утверждённого запрета или процента в таблице**. Таблица из пункта 5.1 и явные запреты имеют приоритет.

### 5.3. Качество заброса

Цель — 80% шкалы заброса. Градации по абсолютному отклонению:

| Отклонение | Оценка | Множитель редкости `Q` |
|---:|---|---:|
| до 6 процентных пунктов включительно | Супер | 1,80 |
| свыше 6 до 12 п. п. | Отлично | 1,40 |
| свыше 12 до 20 п. п. | Хорошо | 1,00 |
| свыше 20 до 35 п. п. | Неплохо | 0,70 |
| более 35 п. п. | Неудачно | 0,40 |

При `Q=1` точно сохраняется таблица пункта 5.1. Для редкостей выше класса удочки допускается понижение базового шанса при плохом забросе, но не повышение выше утверждённого базового потолка: `P_above = P_base * min(1,Q)`. Заблокированные редкости всегда получают `0`, независимо от `Q`.

Остаток вероятности распределяется среди классов, разрешённых по уровню удочки, пропорционально весам: для обычной и необычной `W=P_base`, для редкой/легендарной/мифической `W=P_base*Q`. Затем `P_allowed = remaining * W/sum(W_allowed)` и итог нормализуется до 100% без отрицательных значений. Следует выполнять расчёты с `double` и округлять **только при отображении**, чтобы на всех качествах сумма была 100%.

**Пример для удочки мастера и качества «Супер»:** обычная 28,42%; необычная 18,95%; редкая 25,58%; легендарная 17,05%; мифическая 10%.

## 6. Бонусы удочек при вываживании

| Удочка | Бонус к приросту шкалы внутри зоны | Множитель прироста | Скорость движения зелёной зоны вверх при удержании | Скорость падения вниз при отпускании | Время восстановления рыбы |
|---|---:|---:|---:|---:|---:|
| Тренировочная | 0% | ×1,000 | 0,530 ед./с | 0,340 ед./с | 2 с |
| Новичка | +2,5% | ×1,025 | 0,530 ед./с | 0,340 ед./с | 4 с |
| Хорошая | +5% | ×1,050 | 0,530 ед./с | 0,340 ед./с | 6 с |
| Мастера | +10% | ×1,100 | 0,530 ед./с | **0,357 ед./с (+5%)** | 8 с |
| Прочитателя | +15% | ×1,150 | 0,530 ед./с | **0,374 ед./с (+10%)** | 10 с |

**Принципиальное уточнение:** при удержании пальца зелёная зона идёт **вверх** со старой скоростью 0,53 ед./с для всех удочек. Удочки мастера и прочитателя ускоряют **только падение вниз после отпускания пальца во время вываживания**. Ранее предлагавшиеся значения 0,5565 и 0,583 для движения при удержании **отменены**.

```
zoneY += dt * (held ? -0.53 : (0.34 * fallMultiplier[rod]))
fallMultiplier = [1.00, 1.00, 1.00, 1.05, 1.10]
zoneY = clamp(zoneY, 0.0, 0.75)
```

Бонус прироста шкалы не добавляет разовый процент; он умножает скорость заполнения и не зависит от FPS.

## 7. Итоговые формулы вываживания

### 7.1. Движение рыбы

Переопределение направления каждые `0,27..0,70` с:

```
newVelocity = (random01 - 0.5) * 1.18 * raritySpeed[r] * (shimmering ? 1.20 : 1.00)
```

При развороте или касании границы у неуставшей рыбы действует прежний импульс до +22% на 0,30 с:

```
turnBoost = tired ? 1.0 : 1.0 + 0.22 * (turnBoostLeft / 0.30)
movementFactor = tired ? 0.70 : 1.0
fishY += newVelocity * dt * movementFactor * turnBoost
```

После усталости `turnBoostLeft` следует обнулять, а на границах **не** активировать новый рывок, пока рыба остаётся уставшей (включая RECOVERING). Новая система заменяет прежнее *обратимое по прогрессу* замедление движения на 15% при 70% и 30% при 90%, доступное раньше только некоторым удочкам. Замедление рыбы теперь общее для всех удочек и определяется состоянием усталости.

### 7.2. Заполнение и потеря шкалы

Базовые показатели источника: `P_start=0,28`; при попадании рыбы в зелёную зону — `+0,26` шкалы/с до модификаторов; вне зоны `-0,12` шкалы/с. Определение попадания использует реальную видимую ширину зелёной зоны, зависящую от редкости и мерцания.

```
massRatio = clamp((mass - massMin[r]) / (massMax[r] - massMin[r]), 0, 1)
fillTime = rarityFillTime[r] * (1 + 0.12*massRatio)
shimmerFactor = shimmering ? 0.75 : 1.0
rodFillBonus = [0, 0.025, 0.05, 0.10, 0.15][rod]
trainingLateFill = rod==0 ? (P>=0.90 ? 0.70 : P>=0.70 ? 0.85 : 1.0) : 1.0
G = 0.26 * (1 + rodFillBonus) * shimmerFactor * trainingLateFill / fillTime
P = clamp(P + dt * (insideZone ? G : -0.12), 0, 1)
```

Восстановление / включение усталости должно оцениваться **после обновления `P`** в кадре. Рыба поймана при `P>=1`, сорвалась при `P<=0`. Поздний штраф заполнения тренировочной удочки 0,85/0,70 сохраняется, **но это не штраф движения рыбы** и не отменяет общий механизм временной усталости.

Пример: легендарная 5 кг, удочка мастера, без мерцания, постоянно внутри зоны: около **+16,59 процентных пункта/с**. Мифическая 10 кг с удочкой прочитателя, без мерцания: около **+14,25 процентного пункта/с**.

### 7.3. Поклёвка и старые находки

Сохраняется шанс поклёвки **только при подтягивании**:

```
lambda = 0.40 + 0.52 * distance
pBite = 1 - exp(-lambda * dt)
```

Начало игры: 10 наживок; одна наживка тратится на один заброс. При неудачном забросе шанс старой обложки 25%. Старая обложка не даёт XP и золота и не проходит механики рыбы/усталости.

## 8. Награды и экономика — без изменений

| Редкость | XP на 1 кг | Золото на 1 кг до округления | Коэффициент награды `K` |
|---|---:|---:|---:|
| Обычная | 20 | 5 | 1 |
| Необычная | 30 | 7,5 | 1,5 |
| Редкая | 50 | 12,5 | 2,5 |
| Легендарная | 80 | 20 | 4 |
| Мифическая | 140 | 35 | 7 |

```
XP   = round(20 * massKg * K)
Gold = max(1, round(5 * massKg * K * (shimmering ? 3 : 1)))
```

В магазине: 1 наживка — 30 золота; 10 — 270; 50 — 1200. Стоимость удочек приведена в пункте 5.1. Покупки остаются постоянными, выбранная удочка сохраняется.

## 9. Техническая интеграция (когда будет дана команда реализовать)

- `ChteicoFishingView.java`: новые значения шансов и фильтр запретов; бонусы удочек; отдельные состояния `FULL_STRENGTH/TIRED/RECOVERING`; игровой таймер; рендер индикатора над рыбой; сброс на новой попытке.
- `ChteicoStore.java`: существующие данные об удочках, ценах, наживке и наградах **не менять**; при необходимости брать `rod` из текущей выбранной удочки.
- `view_chteico_fishing.xml`: отдельный overlay поверх рыбы; индикатор не должен принимать касания (`clickable=false`), мешать прокрутке или закрывать полосу прогресса.
- Новый вектор `ic_fishing_fatigue_debuff.xml`: привязать к теме через `setColorFilter()` (цвет текста/иконок), как другие значки.
- Кольцо и заполнение таймера: прорисовка в отдельной View или существующем слое с `Canvas.drawArc`, анимация плавная; длительность и прогресс вычисляются от игрового `dt`, а не от жёсткой продолжительности `AnimatedVectorDrawable`.
- Состояние индикатора не должно зависеть от поворота `ImageView` рыбы; использовать отдельную геометрию overlay.
- При `pauseClock()`, `resumeClock()`, `stopClock()`, уничтожении/повторном открытии активити и окончании игры не оставлять «висящих» анимаций.
- Все новые визуальные элементы обязаны следовать выбранной теме приложения (дневная, ночная, мягкая, сепия, пользовательская).

## 10. Проверки при реализации

1. Все пять редкостей и мерцающие экземпляры достигают точных порогов 90/80/70/65/60% и минус 5 п. п.; граничное равенство `P == threshold` считается усталостью.
2. Состояние TIRED уменьшает скорость на 30% и обнуляет рывки на поворотах независимо от удочки.
3. Уход ниже порога запускает обратный отсчёт; возврат на порог до нуля **сбрасывает** отсчёт; истечение ниже порога возвращает FULL_STRENGTH; новый набор порога снова утомляет рыбу.
4. Таблица таймера по удочкам: 2/4/6/8/10 с; счётчик не продвигается во время паузы.
5. Индикатор всегда выше рыбы, никогда не перевёрнут и не обрезан при движении к верхней/нижней границе; плавное кольцо работает вместе с динамическим таймером.
6. Тренировочная никогда не получает редкую/легендарную/мифическую; хорошая никогда не получает легендарную/мифическую, включая «Супер».
7. Удочка новичка сохраняет разрешённые редкости и их утверждённые шансы 60/16/10/8/6 при «Хорошо» (особый согласованный баланс).
8. Для каждого класса удочки и каждого качества заброса сумма вероятностей 100% в расчётах до округления и нет отрицательных значений.
9. Прирост шкалы (0/2,5/5/10/15%) рассчитывается по `dt` и не меняется от частоты кадров.
10. Падение зоны **после отпускания** 0,34/0,34/0,34/0,357/0,374 ед./с; движение **при удержании** 0,53 ед./с у всех удочек.
11. Проверить массу, ширину зоны, мерцание, золото, XP, старую обложку, наживку, сохранение покупки и выбор удочки без регрессий.
12. Проверить на светлой и тёмной темах: цвет вектора, читаемость окружности и отсутствие контурных «самодельных» кнопок.
