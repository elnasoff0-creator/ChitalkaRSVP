# ПРОЧиталка v1.11.132-beta CLEAN HOTFIX — техническая расшифровка

**База:** v1.11.131-beta CLEAN HOTFIX (включая исправление типов `chapterTitleForWord(...)`).  
**Версия:** `versionName 1.11.132-beta`, `versionCode 13200`.  
**Формат:** полный Java/Android проект; Android APK не включён.

## 1. SQLiteOpenHelper — новое хранилище словаря Edge TTS

Новый `EdgeDictionaryStore.java` расширяет `android.database.sqlite.SQLiteOpenHelper`. База находится во внутреннем хранилище приложения: `edge_dictionary_v132.db` (таблица `rules`, индексы по типу и порядку/названию). Дополнительные библиотеки и зависимости для SQLite не подключались.

Колонки: `id`, `kind` (замена/игнорирование), `pattern`, `context`, `replacement`, `is_regex`, `ordinal`.

Лимиты приложения:

- 10 000 обычных замен;
- 1 000 Regex-правил **суммарно** для обеих вкладок;
- 5 000 обычных правил игнорирования;
- длина шаблона до 400 символов, замены — до 1 000, контекста — до 240.

При первом доступе к словарю происходит однократная миграция существующих записей из `SharedPreferences` в SQLite в одной транзакции. Прежние значения не стираются и остаются резервной копией. Миграция старого примера `***=.` переносит символы `***` в игнорирование, не создавая лишнюю произносимую точку. Маркер миграции записывается только после успешной транзакции.

Записи сохраняются сразу после добавления/редактирования/удаления. Редактор выводит ограниченное количество записей (по 100) и подгружает следующие по запросу; поиск производится по SQLite. Есть числовой счётчик правил.

## 2. Регулярные выражения в заменах и игнорировании

В `EdgeDictionaryActivity` добавлен переключатель **«Регулярное выражение (Java Regex)»**. При выключенном переключателе действует привычный точный поиск текста, с необязательным контекстом. Для Regex контекст отключается; подстановки `$1`, `$2`, `${имя}` поддерживаются в поле замены. Пустая замена означает удаление совпадения. Для вкладки «Игнорировать» совпадение всегда исключается из отправляемого в Edge TTS текста.

На Android Unicode-классы символов и Unicode-регистр доступны без `Pattern.UNICODE_CHARACTER_CLASS`: платформа этот флаг не поддерживает. Для пользовательских Regex применяется единый метод `compileUserRegex(expression)`, автоматически выбирающий допустимый набор флагов; `(?iu)` можно задавать внутри выражения, как в примерах. Некорректные выражения и неправильные номера групп проверяются до сохранения; часть очевидно тяжёлых выражений с вложенными повторениями отклоняется. Защита не является гарантией ограничения времени выполнения произвольного Regex; при тысячах сложных правил скорость зависит от их содержимого.

**Примеры:**

| Найти (Regex) | Заменить на | Что произойдёт |
|---|---|---|
| `(?iu)\bполк[ауи]\b` | `полка` | «полка», «полку», «полки» → «полка» |
| `(?iu)\bгл\.\s*(\d+)` | `глава $1` | «гл. 12» → «глава 12» |
| `(?m)^[ \t]*\r?\n` | *(пусто)* | Удаляет пустые строки между абзацами |
| `\*` | *(пусто)* | Удаляет звёздочки |

Вкладка **«Игнорировать»** получила готовый пункт **«Убрать пустые строки · Regex»**; по нажатию открывается редактируемое правило, чтобы пользователь мог проверить и сохранить его.

Редактор предоставляет **предварительную проверку правила** на введённой фразе и озвучивание преобразованного результата. Сохранены ранее существовавшие «Из предложения», контекстные обычные замены, символы и выбор ударения нажатием на гласную. Выбор ударения скрыт при Regex.

## 3. Работа с Edge TTS и подсветкой

Изменения в `EdgeSpeechTextTransform.java`: введены скомпилированные записи `Entry` и объект `Options`, загружаемый с учётом ревизии SQLite. Правила игнорирования применяются до замен; позиции преобразованных символов сопоставляются с оригинальным текстом книги. Сохраняется прежняя цепочка `Result.aligned(...)` для `WordBoundary`, а также отдельные ключи аудиокэша в зависимости от фактически отправленного текста.

Новый словарь используется **и потоковой озвучкой** (`EdgeStreamingService`), **и подготовкой всей книги** (`EdgeFullBookService`). Движки получают набор правил из общего хранилища. SQLite не опрашивается на каждое произносимое слово; подготовленные правила компилируются/сортируются при смене ревизии, а между фрагментами переиспользуются.

Случаи сложной перестановки слов через группы Regex могут дать несовершенное сопоставление `WordBoundary`. Поэтому в справке рекомендуется тестировать такие правила на фрагменте книги. Исходный EPUB/FB2/HTML и визуальный текст ReaderActivity не меняются.

## 8. Исправление HOTFIX: Android Regex Unicode

**Проблема v1.11.132 CLEAN:** на Android `Pattern.compile(expression, Pattern.UNICODE_CHARACTER_CLASS)` выбрасывал `IllegalArgumentException: UNICODE_CHARACTER_CLASS flag not supported`. Это затрагивало предварительный просмотр правил, сохранение Regex в SQLite и построение списка скомпилированных правил для Edge TTS. Тесты на настольной Java не выявили несовместимость.

**Исправлено:** все три пути используют `EdgeSpeechTextTransform.compileUserRegex(expression)`, который проверяет сложность, один раз определяет поддержку Unicode-флага и на Android передаёт `0` вместо неподдерживаемого флага. На обычной JVM Unicode-флаг включается для корректных тестов `\b` с кириллицей. На Android Unicode-классы включены по умолчанию; пользовательские `(?i)`, `(?iu)`, `(?m)` остаются допустимы. SQLite-хранилище, существующие записи и версия приложения не изменены.

**Дополнительный тест:** `qa/test_v11132_android_regex_compat.py` проверяет отсутствие прямого использования флага в редакторе и SQLite, безопасную проверку поддержки в общей функции и её применение при озвучивании. Этот тест дополняет JVM-тесты кириллицы, групп `$1`, пропуска пустых строк и сопоставления WordBoundary.

**Ограничение:** локальные JVM/Android API-заглушки и статический контракт не заменяют инструментальный запуск на телефоне и CI `:app:assembleRelease`.
